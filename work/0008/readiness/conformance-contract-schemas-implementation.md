and its eight manifest entries. Its governing requirements are R-0005-034,

  versus breaking-major rules, and exact specification/profile/ordered

  implementation/artifact-set identities, capability dispositions,

- R-0008-011 through R-0008-015 fix the evidence-kind vocabulary, non-empty
  `all-of`/`any-of` recipe semantics, finite executable bounds, evidence

- R-0005-034/035 and R-0008-022 require exact-byte root-manifest promotion,

  disclosure-policy weakening. These are schema constraints where structural
  and validator-enforced policy where content or external state must be
  inspected.

These rules support closed local object shapes, explicit enums and required
properties. They do not by themselves define a universal JSON Schema
representation or make every cross-object rule enforceable in JSON Schema.

### Blockers

1. **No reviewed seven-format/schema-ID mapping or dialect.** I-0008-017
   requires review of the seven format identities and schema identifiers as
   concrete representations, but none are listed in its manifest or resolved
   in the reviewed specification/decision sources. Existing
   `operation-descriptor-v1alpha1` uses Draft 2020-12 and a stable `$id`;
   the schema convention requires stable offline references and new versions
   for breaking changes. R-0007-348's Draft 2020-12 rule applies to the
   embedded Qhapaq schema profile, not explicitly to these outer contracts.
   The repository schema convention does not otherwise select a dialect for
   them. Resolve the exact `$schema`, `$id`, format literal, and compatibility
   identity/version of each of the seven contracts; do not infer all seven
   from filenames or extend the embedded-profile dialect rule.

2. **Digest algorithm/encoding and validation boundary are not assigned.**
   R-0008-012/022/024 and R-0005-034/035 require content-addressed objects and
   exact digests, while I-0008-017 requires digest-shape/mismatch checks.
   Those sources do not define one digest algorithm, byte scope, or textual
   encoding for the new evidence, publication, artifact-set, and release
   objects. R-0005's SHA-256 checksum language and the operation-descriptor's
   `sha256:` contract digest cover other stated artifacts; they do not state
   that this choice applies to every new identity. Also, schemas can constrain
   digest syntax but cannot verify the digest against referenced bytes.
   Identify which constraints are schema-level and which require a named
   semantic validator, without weakening exact-byte bindings.

3. **R-0008-022 report representation is not in the manifest.** The requirement
   separately names each conformance report and evidence bundle as immutable
   content-addressed artifacts. I-0008-017 includes the evidence-bundle
   schema but no report schema or explicit mapping of a report to an existing
   declaration/evidence representation. I-0008-003 also lists reports as a
   distinct delivery outcome. Decide through an authoritative contract whether
   the report is an existing defined rendering/artifact or requires a schema
   and owner; do not equate it with the declaration or evidence bundle by
   assumption.

4. **Single-document schema checks are mixed with cross-record policy tests.**
   I-0008-017 asks schema validation to cover exhaustive profile-specific
   obligation sets, digest mismatch, approval-to-bytes binding, lifecycle
   transitions, and edge promotion. A schema can close local shapes and
   validate types/enums/conditional presence; it cannot establish an external
   digest match, completeness against a selected profile, immutability across
   history, or that a release event was protected. The slice has no validator
   implementation or test artifacts in its exact manifest. Assign those
   checks to an existing/approved consumer boundary or revise the validation
   gates to distinguish structural schema results from semantic validation.
   Do not report structural acceptance as proof of cross-record consistency.

5. **Null, omission, and failure representation are not fully enumerated.**
   R-0008-009 explicitly rejects missing required fields and unknown values,
   and R-0008-010/013/024/025 define explicit invalid/unsuccessful states.
   However, the contracts do not specify field-by-field whether an optional
   property may be explicit `null`, whether null differs from omission, or
   whether a nullable reference represents absent evidence/status. I-0008-017
   does not list that matrix or corresponding valid/invalid cases. Before
   authoring, map required, optional, and nullable properties per format and
   preserve omission/null distinctions where the governing requirement
   distinguishes them; do not encode `null` as a success-shaped default.

6. **Required reproducible schema validation command is not established.**
   I-0008-017 requires every schema to validate against the repository's
   documented dialect and every reference to resolve offline, but the schema
   authoring convention gives no dialect-specific tool/command. I-0007-002 and
   I-0007-005 remain open milestones with no approved concrete commands or
   artifact manifests; they are downstream prerequisites of I-0008-019, not
   dependencies of I-0008-017. The present slice nevertheless needs a
   reproducible validator/dialect check and durable valid/invalid evidence
   within its approved boundaries, not an undocumented one-off result.

7. **Vector coverage/ownership does not yet prove all schema families.**
   I-0008-019 assigns profile, declaration, assessment, evidence, publication,
   and lifecycle vectors and depends on the future shared tooling/foundation.
   Its current exact manifest has no root-release-manifest vector and no
   report artifact case; its publication cases do not define external
   digest-verification or a rejected lifecycle-transition sequence. I-0008-017
   itself has no conformance-instance files in its manifest, while R-0007-347
   requires exact portable artifact versions and expected results before
   dependent implementation is complete. Reconcile the downstream vectors
   and tests to cover the release-manifest and report boundary and the
   cross-record failures assigned above; retain I-0008-019's actual
   I-0007-002/I-0007-005 prerequisites rather than pretending those artifacts
   exist.

These are contract/manifest/test-boundary findings, not new accepted product
semantics. No JSON Schema dialect, digest format, null policy, report identity,
or artifact equivalence is selected in this assessment.
